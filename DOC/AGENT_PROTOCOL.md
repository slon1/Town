# AGENT_PROTOCOL — как работать с инструкциями архитектора

Документ обязателен для **Grok** и **Composer** (Cursor). Читать полностью перед каждой новой задачей.

## 1. Роли

- **Архитектор** (Claude): пишет ADR и TASK, принимает работу на майлстоунах. Имеет доступ на чтение git и чат с оператором. Проект сам не меняет.
- **Оператор**: передаёт сообщения между архитектором и Cursor, принимает решения по неясностям.
- **Исполнитель** (Grok/Composer в Cursor): полный доступ к проекту, сценам, MCP, git. Реализует задачу, пишет рапорт, обновляет git.

## 2. Иерархия источников истины

1. `DOC/adr/*` — архитектурные решения.
2. `DOC/tasks/*` — текущая задача.
3. `DOC/PLAN.md` — контекст и порядок.
4. Код.

При противоречии между уровнями — **остановиться и задать вопрос оператору** (формат в п. 7). Не угадывать.

**Документы `DOC/adr/*` и `DOC/tasks/*` исполнитель не редактирует** (только архитектор; на диск их кладёт оператор). Если на диске нет версии, которую требует задача (в заголовке задачи — «Требуемые версии»), исполнитель **останавливается и сообщает оператору**, а не переписывает документы сам. В первом сообщении по задаче исполнитель называет версии прочитанных документов (маркер версии — в строке «Статус» ADR и в заголовке TASK).

## 3. Жёсткие ограничения проекта

- Unity **6000.5**, C#, DOTween v2 **1.3.045**, Extenject (Zenject) **9.2**, UniTask **2.5.11** (define `UNITASK_DOTWEEN_SUPPORT` включён).
- **asmdef — только там, где необходимо** (решение оператора). Сейчас разрешены ровно два: `ZombieCity.City.Core` (чистый C#, `noEngineReferences = true`) и тестовая EditMode-сборка. Остальной код — штатные сборки (`Assembly-CSharp`, `Assembly-CSharp-Editor`); Editor-код — только в папках `Editor`. Новый `asmdef` сверх этого — только с обоснованием в рапорте и согласованием с архитектором.
- Render pipeline: **URP**. Фреймворк частиц и агенты в текущих задачах **не используются** и не трогаются.
- UI: Canvas **Render Mode = Screen Space – Camera**, Canvas Scaler **Scale With Screen Size, 1080 × 2160**.
- Новые пакеты и сторонние библиотеки добавлять **только если разрешено в ADR/TASK**. Вендорный код — в `Assets/_Project/ThirdParty/` с файлом лицензии.
- Namespace: `ZombieCity.<Модуль>` (например, `ZombieCity.City.Core`, `ZombieCity.City.EditorTools`).
- Core-код (парсер, модель, растеризатор) лежит в `Scripts/Runtime/City/Core/` под `asmdef` с `noEngineReferences = true` и **не использует типы UnityEngine** (компилятор это обеспечит). Используются `double`-структуры (`Vec2d`). Ассеты-контейнеры (`ScriptableObject`) живут вне Core и ссылаются на него.
- Рантайм-код без аллокаций в горячих путях; без LINQ в циклах по клеткам/частицам. Bake-код может аллоцировать разумно.
- Async — через UniTask; в Editor-bake длинные операции показывают `EditorUtility.DisplayProgressBar`.
- Логи с префиксом `[City]`; без спама (итоговая статистика, предупреждения агрегированно со счётчиками).
- Коммитить `.meta`-файлы. Не изменять сцены и префабы вне объёма задачи. Любые изменения сцен через MCP описывать в рапорте.
- Нет `FindObjectOfType`, нет статических синглтонов в новом коде; зависимости — через Extenject (когда код живёт в сцене/рантайме). Исключение: Editor-код (меню, `[InitializeOnLoad]`, `EditorPrefs`, статические Editor-утилиты).

## 4. Рабочий цикл по задаче

1. Прочитать `DOC/PLAN.md`, указанные в задаче ADR, саму задачу.
2. Проверить `git status`; определить основную ветку (`git symbolic-ref refs/remotes/origin/HEAD`), создать от неё `task/NNN-<slug>`. Не делать force-push. Основную ветку не менять напрямую.
3. Выполнять **подшаги по порядку**. После каждого подшага:
   - проект компилируется без ошибок и новых предупреждений;
   - выполнены критерии подшага;
   - коммит **и `git push` после каждого подшага**: `[TASK-NNN/<шаг>] краткое описание` (архитектор читает git и видит ход работы).
4. Подшаги, помеченные в задаче как «самоприёмка», принимает сам исполнитель (Grok проверяет по критериям). Архитектор проверяет итог всей задачи/майлстоуна. Не ждать архитектора между подшагами.
5. По завершении: создать `DOC/reports/REPORT-NNN.md` по шаблону (п. 8), отметить статус в `DOC/PLAN.md` (только чекбокс), запушить ветку, сообщить оператору.
6. После вердикта архитектора — исправить замечания отдельными коммитами `[TASK-NNN/fix]`.

## 5. Распределение по моделям

- Каждая задача (`TASK-NNN-<модель>-<slug>.md`) предназначена **одному** исполнителю, указанному в заголовке («Исполнитель»). Оператор передаёт её вручную. Смешанных задач нет.
- Исполнитель, получивший задачу с чужой моделью в заголовке, **останавливается и сообщает оператору**.
- **Grok**: алгоритмы, геометрия, правила ADR, анализ, всё с архитектурными решениями внутри рамок. **Composer**: Editor-инструменты, окна, экспорт, механические правки по явному списку.
- В рапорте указывается фактическая модель (название и версия), а не плановая.

## 6. Допустимая самостоятельность

Можно самостоятельно: выбирать имена приватных членов, структуру внутренних классов, вспомогательные методы, оптимизации внутри контракта.

**Нельзя без согласования**: менять публичные контракты из ADR (структуры данных, значения флагов, форматы ассетов, единицы измерения, систему координат), добавлять пакеты, менять правила приоритета слоёв, выходить за объём задачи («заодно» не делать). Если контракт мешает — оформить `ADR-change-request` в рапорте (что, почему, предложение) и продолжить в рамках существующего контракта, либо остановиться, если продолжать нельзя.

Шаблон `ADR-change-request` (в рапорте):
```
ADR-change-request: <ADR-N §X>
Что мешает: ...
Предложение: ...
Влияние: (какие файлы/контракты/форматы)
Продолжил ли в рамках текущего контракта: да/нет
```

## 7. Когда останавливаться и спрашивать

Остановиться и задать вопрос оператору, если:
- задача неполна, двусмысленна или противоречит ADR;
- не хватает входных данных (файлы, API фреймворка);
- результат не соответствует ожиданиям из критериев, и причина неясна после 2 попыток;
- требуется нарушить ограничения из п. 3.

Формат вопроса: `ВОПРОС: <суть>` / `Контекст: <что делал>` / `Варианты: A) ... B) ...` / `Рекомендую: <вариант>`.

## 8. Шаблон рапорта `DOC/reports/REPORT-NNN.md`

```markdown
# REPORT-NNN — <название задачи>
- Ветка / коммиты: ...
- Исполнитель (модель): ...
## Что сделано (по подшагам, с отметкой самоприёмки)
## Критерии приёмки — таблица: критерий | результат | цифры/доказательство
## Цифры (статистика импорта, время, размеры ассетов, хэши)
## Отклонения от ТЗ и почему
## ADR-change-request (если есть)
## Известные проблемы / ограничения
## Вопросы к архитектору/оператору
## Как проверить (меню, сцены, ассеты)
```

Рапорт краткий, с цифрами. Без пересказа кода.

## 9. Качество кода

- Читаемость важнее хитрости. Комментарии — для неочевидных решений (геометрия, приоритеты слоёв), с отсылкой на ADR.
- Детерминизм: никакого `Dictionary`-порядка в выходных данных без явной сортировки; никакого `System.Random` без фиксированного seed.
- Числа и пороги — в `ScriptableObject`-настройках или константах с именами, не «магические».
- Публичное API — XML-doc для классов/методов, входящих в контракты ADR.
