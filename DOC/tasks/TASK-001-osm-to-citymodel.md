# TASK-001 — OSM → CityModel (фаза P1)

- **Модель:** Grok (подшаг 1A — Composer)
- **ADR:** `DOC/adr/ADR-001-city-bake-pipeline.md` (разделы 3, 4, 8)
- **Ветка:** `task/001-osm-citymodel`
- **Приёмка:** подшаги — самоприёмка Grok; итог — архитектор.
- **Перед началом:** прочитать `DOC/AGENT_PROTOCOL.md`, `DOC/PLAN.md` (разделы «Решения оператора» и «Решения архитектора») и **ADR-001 целиком**.
- **Редакция:** v2.1 (учтены вопросы Cursor; решения — `DOC/PLAN.md` §6, «Решения архитектора»).

## Цель

Редакторный импорт `.osm` → `CityModelAsset` (векторная модель в метрах) со статистикой и визуальной проверкой через gizmo. Растеризация **не входит** в задачу (это TASK-002).

## Входные данные

- Файл района: **`Assets/Source/map.osm`** (экспорт напрямую с openstreetmap.org; bbox ≈ 52.553081, 13.377045, 52.557431, 13.387088, Berlin, ≈ 680×480 м). Если файла нет — остановиться и спросить оператора.
- Экспорт с сайта отдаёт ways целиком, но relations (мультиполигоны) может отдавать с неполным набором членов. Парсер обязан быть к этому терпим; **долю потерянных мультиполигонов обязательно указать в рапорте** — по ней архитектор решит, нужна ли выгрузка через Overpass.
- Создать `DOC/data/README.md`: источник (экспорт openstreetmap.org), bbox, дата выгрузки (по метаданным файла/коммита), лицензия «© OpenStreetMap contributors, ODbL».

## Вне объёма

Растры, меш зданий, сцена, Extenject, UI. Фреймворк частиц, агенты, поля управления, сетка солдат — **не трогать и не создавать**. Не добавлять пакеты (кроме встроенного Unity Test Framework, если его нет в проекте; LibTessDotNet понадобится только в P4).

## Подшаги

### 1A (Composer) — каркас
- Создать структуру папок из `DOC/PLAN.md` §4 (`Assets/_Project/...`, с `.gitkeep` где пусто).
- Создать **ровно два `asmdef`**: `ZombieCity.City.Core` в `Scripts/Runtime/City/Core/` (`noEngineReferences = true`, `autoReferenced = true`, `rootNamespace = ZombieCity.City.Core`) и `ZombieCity.City.Core.Tests` в `Tests/EditMode/` (только платформа Editor, ссылки на Core, `UnityEngine.TestRunner`, `UnityEditor.TestRunner`, NUnit через `overrideReferences`, `defineConstraints: UNITY_INCLUDE_TESTS`). Проверить, что `Assembly-CSharp` и `Assembly-CSharp-Editor` видят типы Core.
- Настройки в два слоя (парсеру в Core нельзя ссылаться на `ScriptableObject`):
  - `CityBakeConfig` — `[Serializable]` обычный класс в **Core** (только данные + `CanonicalBytes()` по ADR §4 — сам метод пишет Grok в 1B; в 1A — пустая заглушка);
  - `CityBakeSettings : ScriptableObject` (`Assets/_Project/City/Settings/CityBakeSettings.asset`) в `Assembly-CSharp`, содержит поле `CityBakeConfig config`.
- Поля `CityBakeConfig` (значения по умолчанию из ADR): таблицы ширин по классам (`Road`, `Walkway`), `lanes` → 3.0 м/полоса, `defaultBuildingHeight` (12), `metersPerLevel` (3.0), `roofLevelMeters` (1.5, использовать ли — флаг), `minBuildingHeight` (3), списки допустимых значений тегов (highway/barrier/railway/landuse/leisure/natural), `waterwayWidth` (4.0), опциональный crop-bbox. **Параметры P2 создать сразу**, чтобы не менять формат хэша позже: `cellSize` (0.5), `sidewalkWidth` (2.0), `sidewalkSearchRadius` (4.0), `barrierWidth` (0.5), `crosswalkWidthFallback` (3.0).
- **Anti-scope для 1A:** не писать парсер, модель, геометрию, меш и растеризацию. Только каркас, настройки и заглушки меню.
- Меню `ZombieCity/City/Import OSM...` (пока заглушка с выбором файла).
- Убедиться, что `.gitignore` стандартный для Unity и `.meta` коммитятся.
- **Критерий:** проект компилируется, пункт меню виден, ассет настроек создаётся и открывается в инспекторе, пустой тест в Test Runner (EditMode) запускается и проходит. Самоприёмка.

### 1B (Grok) — Core-модель
- Чистый C# в `Scripts/Runtime/City/Core/` под asmdef `ZombieCity.City.Core` (namespace `ZombieCity.City.Core`): `Vec2d`, enum'ы и структуры модели по ADR-001 §4, плоские массивы + `ringStart[]`.
- `CityModelAsset : ScriptableObject` в `Scripts/Runtime/City/` (сериализуемая модель, метаданные, статистика, хэш).
- Хэш данных и хэш настроек: FNV-1a 64 по каноническому представлению **строго как в ADR-001 §4** (little-endian, миллиметры, UTF-8, порядок сущностей). Для проверки добавить тест с фиксированным ожидаемым значением хэша на мини-фикстуре.
- **Критерий:** модель сериализуется Unity и переживает reload домена; хэш стабилен. Самоприёмка.

### 1C (Grok) — парсер OSM XML и проекция
- Потоковый парсер на `XmlReader` (без `XDocument`): nodes (`id → lat/lon`), ways (список node refs + теги), relations (только `type=multipolygon`, члены ways с ролями `outer/inner`, теги).
- Поддержать: `<bounds>`, `visible="false"` (пропускать), отсутствие `<bounds>`, теги с пробелами/юникодом.
- Проекция по ADR-001 §3.
- Формат входа — только OSM XML 0.6; `.pbf` и прочие форматы не поддерживать. Ссылки на отсутствующие узлы/ways — пропускать с агрегированным предупреждением, не падать.
- **Критерий:** файл района читается без исключений; в логе — количество nodes/ways/relations, время. Самоприёмка.

### 1D (Grok) — классификация и геометрия
- Применение правил тегов из ADR-001 §4 → `Road`, `Walkway`, `Area`, `Barrier`, `Railway`, `Waterway`, `PointFeature`. Правила однозначности (`highway` решает Road/Walkway, теги доступа не учитываются, `building:part` игнорируется) — из ADR §4.
- Разбор ширины и высоты (все форматы из ADR), `layer`, `bridge/tunnel/building_passage`, `sidewalk=*` → `sidewalkMode`.
- Нормализация колец: замыкание, удаление дублей, ориентация outer CCW / holes CW.
- Сборка мультиполигонов: сшивка outer-ways, присвоение inner, обработка незамкнутых/неполных. Правила тегов relation/way — по ADR.
- **Порядок работы (тесты из ADR, не из кода):** сначала по ADR-001 §4 написать тесты на граничные случаи (мультиполигон с дырой, из двух разнонаправленных outer-ways, без outer, незамкнутый, с отсутствующим членом, самопересечение/дубли узлов, дыра у границы outer, `building_passage` vs `tunnel`, `bridge` + `layer`, `living_street`, `track`), убедиться, что они красные, и только потом реализовывать. Тесты не подгонять под код; расхождение с ADR — вопрос, а не правка теста. Эти тесты входят в набор 1G.
- **Критерий:** на файле района есть здания с дырами (>0, число в рапорте), `tunnel` и `bridge` объекты помечены, переходы (`footway=crossing`) найдены. Самоприёмка.

### 1E (Grok) — импорт-пайплайн и статистика
- Меню `ZombieCity/City/Import OSM...`: file picker с дефолтным путём `Assets/Source/map.osm` (последний выбор запоминать в `EditorPrefs`), выбор `CityBakeSettings` → создание/перезапись `CityModelAsset` с именем `CityModel_<имя .osm без расширения>.asset` в `Assets/_Project/City/Baked/` (для `map.osm` — `CityModel_map.asset`). Перезапись **на месте** (сохранять GUID ассета). Прогресс-бар.
- Сводка в консоль (один блок с префиксом `[City]`): bbox в градусах и метрах, количество объектов по классам, суммарная длина дорог/пешеходных по классам, число зданий, средняя/макс. высота, число зданий с дырами, мостов, туннелей, переходов, **счётчики предупреждений** (отсутствующие ссылки, незамкнутые мультиполигоны, здания без высоты → default), время импорта, хэш данных.
- Повторный импорт того же файла с теми же настройками → **идентичный хэш**.
- **Критерий:** хэш стабилен. Время импорта в рапорте с указанием CPU и режима (Editor, Code Optimization = Release); целевое < 10 с, провал только при > 30 с. Самоприёмка.

### 1G (Grok) — EditMode-тесты
Тестируется только Core (тестовая сборка ссылается лишь на `ZombieCity.City.Core`, без кода из `Assembly-CSharp`). Фикстуры — мини-OSM файлы `Tests/EditMode/Fixtures/*.osm.txt` (каждая < 50 строк XML), читаются с диска по пути относительно `Application.dataPath`.
- проекция (известные точки, допуск 0,05 м; север = +Z, восток = +X);
- разбор `width` / `height` во всех форматах из ADR («6», «6.5», «6 m», запятая);
- ориентация колец (outer CCW, holes CW);
- мультиполигон с дырой; мультиполигон из двух разнонаправленных outer-ways;
- неполный мультиполигон (не падает, счётчик предупреждений +1);
- `tunnel=building_passage` vs `tunnel=yes`; `bridge=yes` + `layer`;
- `living_street` → `isShared`; `track` и `track` + `motor_vehicle=yes`; `waterway` → `Waterway`; `building:part` игнорируется со счётчиком;
- хэш: фиксированное ожидаемое значение на фикстуре; два прогона и перестановка элементов во входном XML дают один хэш.

- **Критерий:** все тесты зелёные в Test Runner (список и итог в рапорте). Самоприёмка.

## Definition of Done — критерии приёмки (проверяет архитектор)

1. Проект собирается без ошибок и новых предупреждений; создано **ровно два** asmdef (Core и тесты), остальных нет.
2. EditMode-тесты — все зелёные (количество в рапорте).
3. Импорт района выполняется, хэш стабилен между двумя запусками (оба хэша в рапорте).
4. Статистика импорта приведена в рапорте полностью; предупреждения объяснены; указана доля неполных мультиполигонов (порог для замены файла на Overpass-выгрузку — **>10 %** мультиполигонов зданий/землепользования; решение остаётся за архитектором).
5. Gizmo-просмотр: скриншот приложен; север/масштаб корректны.
6. Core компилируется с `noEngineReferences = true`; `CityModelAsset` и Editor-код лежат вне Core.
7. Публичные контракты соответствуют ADR-001 (или оформлен `ADR-change-request`).
8. Рапорт `DOC/reports/REPORT-001.md` по шаблону из протокола; ветка запушена.

## Заметки и подсказки (не требования)

- Для point-in-polygon при присвоении inner использовать точку, гарантированно лежащую внутри inner-кольца (не обязательно вершину).
- Размер ожидаемых данных: десятки тысяч узлов; потоковый парсер и массивы `long→(double,double)` через `Dictionary` достаточны.
- Не забывать, что `Dictionary`/`HashSet` не дают стабильного порядка — сортировать перед записью в модель.
- Если в файле нет `<bounds>`, bbox считать по узлам, но предупредить.
